How a request is served

Request / reply + background jobs
Service Message bus Data store Area of my headline contributions (async import queue, PDF pipeline, S3 delivery, SignalR results)

1Synchronous path

The gateway authenticates the JWT, resolves permissions, and stamps a header with tenant, user and correlation IDs. It then publishes a NATS request on a subject such as Core.ProjectDoor.Read and waits for the reply. It never touches a database itself.

2Inside a service

A handler subscribes to a subject root, dispatches by exact subject and sends a MediatR command or query. Pipeline behaviours run FluentValidation and translate Postgres constraint violations into actionable messages. EF Core resolves the tenant's own connection string per request.

3Asynchronous path

Reports, imports and exports become rows in a Postgres jobs table, which workers claim with FOR UPDATE SKIP LOCKED by priority, with attempt limits. Quick jobs answer inline; otherwise the caller gets 202 Accepted and the outcome arrives later over SignalR.

Engineering patterns I work with daily

Observed in the codebase

Uniform layering

All seven services share one project layout and dependencies point inward, so moving between services needs no re-orientation.

Contracts as packages

Request, response and subject definitions ship as versioned NuGet packages, so a service upgrades independently instead of in lockstep.

Tenant isolation by design

Each tenant has its own database and credentials, resolved per request. Isolation is structural, not a WHERE tenant_id a query can forget.

Correct concurrent queue

SKIP LOCKED claiming with priority, attempt limits and a grace window lets workers scale out without double-processing.

Errors written for users

Constraint violations become plain-language messages; internal detail is withheld from anything that isn't a validation failure.

Performance in hot paths

Spreadsheet parsing reads headers by index and iterates only rows with content, avoiding a 1,048,576-row scan on styled files.

Substantial test suite

493 test files spanning unit, mapping, SQL-contract and container-backed integration tests, plus a report-generation volume benchmark.

Comments that explain why

Non-obvious code records the reasoning (why a grace window exists, why a subject is mirrored), not a restatement of the line.

04 · Case study · Jiwa PDF Scanner

Purchase-order PDFs to ERP sales orders: exactly once, for many tenants

A multi-tenant document-to-ERP platform I designed and built at Cipher Impact for a client. Customers email purchase-order PDFs to a tenant's workflow address; the platform reads them, validates every line against the tenant's live Jiwa Financials system, and creates the sales order only when it is safe, and never twice.

From a 722-page specification to a verified release in three weeks.

Jiwa has no draft orders, an order can't be edited after creation, and a duplicate order ships stock twice. So the design treats "do nothing and show a person" as the right answer whenever anything is uncertain, and makes a second order for the same purchase order structurally impossible.

  • Multi-tenant from day one: isolation in the API and the database.
  • Routing by recipient address only, never by sender or PDF content.
  • ERP-neutral core: only the connector knows Jiwa exists.
  • Every failure is a visible exception plus a notification, never just a log line.
  • Non-production can never reach production Jiwa, enforced in config and at call time.

The processing pipeline

Every PDF is an attempt, driven by outbox messages
01

Receive

Mail to {tenant}.orders.{token}@…; tenant and workflow come from the recipient only. Redeliveries are audited and ignored.

02

Store

PDFs verified by their bytes, hashed, and stored under a tenant/workflow prefix. Malware is quarantined; duplicates are held.

03

Extract

Embedded text first, with OCR/AI behind ports. Per-field confidence; the original result is made immutable by a database trigger.

04

Validate

Ordered rules against live Jiwa data: 7 customer-ID methods, 6 item-match methods, 5 pricing modes, units, duplicates, delivery.

05

Create

Reserve, send once, classify the answer. Unknown outcomes are settled by lookup only, never by a resend.

06

Trace

Traceability note on the order, notifications, usage records and an append-only audit trail.

Exactly-once order creation

The part that can't be wrong

Jiwa has no idempotency key, so "exactly once" can't be delegated to the ERP. It's built from database invariants, a strict send discipline and lookup-only recovery: a create request is sent at most once, and an uncertain result is never retried blindly.

Re-check and lock

Transaction-scoped PostgreSQL advisory lock on tenant + workflow + debtor + PO number, then a fresh app-history and Jiwa duplicate check.

Reserve

Insert the transaction as creation_pending. A partial unique index over the active states makes a concurrent attempt fail at the database.

Hand over via the outbox

The reservation commits with an outbox message on a per-tenant FIFO group, so at most one create is in flight per tenant.

Check, mark sent, send once

Re-apply the tenant and commercial gate, record request_sent_at, post once. Only failures that provably never reached Jiwa are retried.

Classify the answer

Order id → created. Business refusal → failed, nothing created. Timeout or 5xx after sending → outcome unknown, and the lock stays.

Settle by lookup only

Search Jiwa by debtor and PO since sending: exactly one match is adopted; none or several go to a person. Nothing is re-sent to find out.

Recover interrupted work

A sweeper settles transactions left pending by a stopped worker, and runs again after a database restore before processing resumes.

Architecture highlights

One .NET 10 solution · Next.js backend-for-frontend

Clean, sliced backend

13 source projects (Domain ← Application ← adapters ← Api, Workers) enforced by architecture tests. 21 feature areas as vertical slices through an in-house mediator.

Reliable messaging

Transactional outbox and inbox; seven worker roles (intake, extraction, validation, ERP, notifications, outbox, sweeper) share one Application layer.

Fail-closed tenancy

Forced row-level security on every tenant table, even for the owner. Settings live and die with each transaction, and missing settings return no rows.

Invariants in the database

Partial unique indexes, CHECK constraints, an immutability trigger, and an append-only audit enforced by revoked grants, not by code paths remembering to check.

Access & audit

12 roles and 65 permissions across platform, partner and tenant organisations, with per-resource conditional grants, an escalation guard and 188 typed audit events.

Tokens never in the browser

A Next.js backend-for-frontend runs OIDC + PKCE server-side, with AES-256-GCM sessions in PostgreSQL, per-request CSP nonces, CSRF checks and a generated proxy allowlist.

Contract-checked connector

Built from the vendor's 778-operation OpenAPI document; failures are normalised into 12 categories that record whether a request may have reached Jiwa.

Contracts pinned end to end

The backend OpenAPI is committed with a drift check, the frontend pins it by SHA-256, and Zod parses every response against the generated types.

06 · How I work

The habits behind the results

The same patterns run through my professional work and my own repositories.

01

Specification before code

Large projects start with a PRD or SRS, architecture docs, decision records and a staged plan. PookieBudget specified its allocation algorithm, with 15 golden vectors, before any code was written.

02

AI-assisted, human-owned

I use coding agents for repetitive work (up to 60% faster delivery), with context-rich prompts, staged plans and handoff docs. I own the hard problems and review every AI-generated line.

03

Correctness where it matters

Money is never a float, ledgers are append-only, prescriptions are versioned, the clock is injected, and file operations are crash-safe.

04

Measure, then decide

Thresholds are chosen by sweeping against ground truth, and the reasoning is written down, including when intuition was wrong (a 0.92 match threshold would have let 21 decoys through).

05

Tests as a gate

100% line and branch coverage held across 3,651 tests on a client platform; 80–85% floors in my own CI, property-based tests, real PostgreSQL via Testcontainers, system tests of built executables, golden files and fuzzing.

06

Security as a programme

Threat models, ISO 27001 control mapping, pinned CI actions, secret scanning, Argon2id, signed documents, and audit trails with soft delete.

07

Performance by design

Long work moves off the request thread, files go through presigned URLs, and hot paths avoid wasted work: 25 s → under 200 ms.

08

Build for real users

A clinic, a retail store, a receipt system and a tax engine: concrete local problems (PKR, lakh grouping, Zakat certificates, Pakistan's tax ordinance) solved end to end.
